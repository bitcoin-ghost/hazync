# A board block proved across three cards — 2026-09-17

**What this is.** The first validation of mode-6 distribution (#361 / #364) on real hardware: block
**74,928** proved end to end across **3 × RTX 4090** and verified against the canonical guest.
Everything here is wall-clock from the retained evidence; nothing is scaled or inferred unless it
says so.

**Why it matters.** Before #364 a *board* block could only be proved in one process. The distributing
path (`seg-serve`) built its session from `build_full()`, which reads a `HAZYNC_BLOCK` fixture and
never touches a bridge bundle, and emitted mode 4 (`KIND_CHUNK`) or the mode-5 aggregate — a block
proof the coordinator does not accept, because `verify_receipt` checks a **`KIND_RANGE`** receipt.
So the fast path was unsubmittable and the submittable path was single-card, however large the block.

⚠ **The binary must be built with `GPU=1`.** Phase 8 of `provision-vps.sh` only sets
`GPU_FEATURES=--features cuda` when `GPU=1`; a bare `cargo build --release --features cuda`
silently produces a **CPU** binary. `build-release.sh cuda` passes `-e GPU=1` into the container,
which is why it is the only supported way to produce this artifact.

⚠ **METHOD_ID cannot be checked on the build box.** A CUDA host needs `libcuda.so.1` to run at all,
so it exits before printing anything on a GPU-less machine — which is *not* the same as reporting a
wrong id. `scripts/check-dist.sh` says so in as many words: *"A CUDA host cannot run on a box without
libcuda.so.1 — it exits before printing anything, which is NOT the same as"* a wrong id, and it offers
`HAZYNC_ATTEST_<artifact>=<id>` for exactly this case. Verified where it runs, on the pods.

## The finding: transport is the bottleneck, not the GPU

| job kind | n | compute p50 | compute p90 | compute max |
|---|---|---|---|---|
| `segment` | 2,353 | 2.83 s | 3.08 s | 11.53 s |
| `join` | 2,352 | **0.38 s** | 0.51 s | 1.89 s |

But the coordinator's own dispatch-to-return timing for the same joins:

| | n | p50 | p90 | max |
|---|---|---|---|---|
| `join` **round trip** | 2,352 | **46.7 s** | 91.0 s | 393.6 s |

**A join costs ~0.4 s of GPU and ~47 s of round trip — a ~120× gap that is entirely transport.**

Per-worker, over 4,706 tasks and **3.53 GB on the wire** (2.55 GB in, 0.98 GB out):

| pod | tasks | segments | joins | segment compute | join compute | **wait** | bytes in/out |
|---|---|---|---|---|---|---|---|
| pod 1 (coordinator + worker) | 2,510 | 916 | 1,594 | 2,609 s | 617 s | 326 s | 1.28 / 0.52 GB |
| pod 2 | 899 | 578 | 321 | 1,573 s | 125 s | **1,855 s** | 0.51 / 0.19 GB |
| pod 3 | 1,297 | 859 | 437 | 2,532 s | 180 s | 834 s | 0.75 / 0.27 GB |

**Pod 2 idled longer than it worked.** It was the only pod on a different host; every byte it moved
went through an SSH hub tunnel on a domestic uplink. Pod 1 — the coordinator's own card, with no
network between it and the queue — did 2.8× pod 2's tasks.

⇒ **3,694 s is not "what three cards do".** It is what three cards do when two of them talk through
home broadband. Adding cards to this topology buys very little; fixing the network buys a lot.

## Honest limits of this run

- **No speedup number.** The single-card reference was stopped after execute (it had reported
  `2353 segments at po2 21`) to save ~1 h of pod time, so there is no same-binary 1-card baseline.
  The comparison target was the board's existing verified receipt instead.
- **No segment-phase transport figure.** The coordinator emits `[rtt]` only for `join` and `lift`
  (2,352 and 1 lines respectively), never for `segment`. The RTT-vs-compute gap above is therefore
  demonstrated for joins only.
- **No GPU telemetry.** 1 Hz sampling was not armed at launch and later attempts failed; there is no
  power or utilisation curve for this run.
- **Drivers differ across the three cards**, so per-card timings are not strictly comparable.
- **#365 is open and untested.** Nothing hung here, but the push transport still has no job deadline:
  a worker that goes quiet stalls the run rather than failing it.

## Reproducing

```sh
# build canonically (NOT a bare cargo build — see the GPU=1 warning above)
SKIP_GROTH16=1 ./prover/build-release.sh cuda

# verify the id WHERE IT RUNS, not on the build box
./hazync-host-x86_64-linux-gnu-cuda method-id     # want 37987b85…

# coordinator
HAZYNC_RANGE=74928 HAZYNC_BRIDGE_OUT=/workspace HAZYNC_PORT=9110 ./host seg-serve

# every worker, INCLUDING one on the coordinator's own card
HAZYNC_WORKER_ID=w1 ./host seg-connect <coordinator>:9110
```

⛔ **Gate reachability before believing any timing.** Same-provider pods get an instant
connection-refused on each other's public ports, and an aggregate in this project once ran N=1 while
*reporting* N=4. Prove that real bytes cross from a worker to the coordinator first.
