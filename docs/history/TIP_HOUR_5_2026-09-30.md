# Tip hour 5 — a cheap measurement run, 2026-09-30

**Two tip blocks, both verified, chain linked. $17.98.** And it answered one of the three questions
it was rented for, blocked two of them on its own fleet size, and found a bug in the instrumentation
that was meant to answer the first.

⛔ **NOTHING HERE IS A MILESTONE.** Seven cards cannot make the 600 s gate and were never meant to:
969,305 took **1,259.3 s** and 969,306 **1,087.5 s**. No wall time on this page belongs in any claim
about following the tip. It is a measurement run and the numbers are diagnostic.

## ✅ #598 — the push dominates, but by 3-4x, not 9x

| block | fetch (bridge → orchestrator) | push (orchestrator → aggregate) | total | ratio |
|---|---|---|---|---|
| 969,305 | 18.7 s | 54.8 s | **73.5 s** | 2.9× |
| 969,306 | 4.8 s | 20.3 s | **25.1 s** | 4.2× |

⛔ **This corrects an off-fleet spot check that claimed 8.8×.** That measurement (pull 4.2 s at
9.85 MB/s, push 37.3 s at 1.12 MB/s over a 41.7 MB bundle) was taken on an **idle link**. Under a live
run the same legs are slower and the ratio is smaller. **The direction held; the magnitude did not.**

⚠ 969,305's numbers are inflated by the fleet still setting up — its fetch ran at 1.59 MB/s against
5.66 MB/s for 969,306 fifteen minutes later. **Judge staging by the second block, not the first.**

969,306's 25.1 s total is below tip hour 4's 49–164 s range. That is consistent with the compressed
push helping, but ⚠ there is **no uncompressed control in this run**, so it is not attributed.

## ⛔⛔ And the instrumentation could not answer it — two ledgers, not one

The run's verdict line read:

    stage: only the 'push' leg was recorded (75.1s over 2) — CANNOT say which leg dominates

The two legs are recorded by different objects passing different directories — `tip_smoke` passes
`a.rundir`, `FleetRunner` passes `self.stage_dir`, and `stage_dir` is `rundir/stage`. So they landed
in **two files** and `verdict()` never saw both. The one question the module exists to answer was
structurally unanswerable. → #611.

⭐ **The control caught it.** Fed one leg, `verdict()` refuses rather than crowning the only leg it
has. It said "CANNOT say" instead of confidently declaring the push the winner off half the data —
a guard written for a different reason, paying for itself on a bug in the same author's code.

## ⛔ #550 — the raw spread is unusable, and that was the whole story until 2026-10-01

| card | n | p50 | p90 |
|---|---|---|---|
| w2 | 896 | **49,404 ms** | 50,171 ms |
| w3 | 414 | 15,913 ms | 17,199 ms |
| w1 | 453 | 5,320 ms | 5,386 ms |

p90 spread **9.3×**, and banking reports 6.0× separation. **Both figures are unusable as stated.**

⚠ w2's **p50** is 49.4 s. Tip hour 4 already established that `[rtt]` is dispatch-to-return and so
includes **queueing** when few cards are attached — it measured 39,000 ms p50 on blocks running with
3–10 cards attached, against ~800 ms later. At 6 working cards that confound dominates, so a raw
percentile here measures queueing, not link quality.

### ⭐ Added 2026-10-01: these logs do answer part of it, with a method that did not exist above

`tip_banks`/`join_levels` gained a cohort view (#619, #624): compare a card only against the cards
it was joining **alongside**, which cancels whatever the batch had in common — including the
queueing that makes the raw percentile useless. Re-run on this run's own two aggregate logs:

| | hour 4 (37 cards) | hour 5 (6 cards) |
|---|---|---|
| raw p90 spread | 12.7× | 6.0× |
| **card effect, cohort-controlled** | 6.5× | **2.9×** |
| **WHICH CARD** share of log(rtt) variance | **17.3 %** | **17.5 %** |
| WHICH DATACENTRE | 12.7 % | 7.8 % |
| WHEN (the batch) | 31.4 % | 26.1 % |
| drop the worst card, off the fold's waiting | 12.9 % | **45.2 %** |

⭐ **The card share lands within 0.2 points of hour 4's**, on a fleet six times smaller. That is the
number #550 needs — a per-card effect stable enough to group by — and this run supplies the
replication, which one run never could.

⭐ **And 45.2 % against hour 4's 12.9 % is the finding, not a discrepancy.** One bad card in six is
in nearly every batch and sets the wall nearly every time; one in thirty-seven is not. A bank *is* a
small fleet, so the fast bank gains more than the whole-fleet figure suggested and the slow bank is
hit harder than the 37-card fleet ever was.

⚠ What is still true from above: this fleet cannot settle the raw-percentile question, and 6 cards
is too few for a split-half persistence check. ⚠ And hour 5's datacentre row rests on **two** groups
covering four of six cards, so it replicates the *ordering*, not the number.

## ⛔⛔ The link probe disagreed with this run, measured 24 seconds apart

This was in the logs all along and I did not look until 2026-10-01.

```
13:59:58  probe:  hz-smoke-3 0, hz-smoke-6 0, hz-smoke-5 1, hz-smoke-10 1 Mbit/s
14:00:22 → 14:01:27  those same four each pulled 410,751,944 bytes from the CDN,
          COMPLETE, in 65 s = 50.6 Mbit/s each — and proved the block.
```

And the one card this run measured **genuinely** slow — hz-smoke-4, 1,754 KB/s, dropped INCOMPLETE —
was **not** among the six the log printed. The log truncates at six with `+3 more`.

⚠ **Not proof the probe is wrong about its own quantity:** it measures aggregate→worker egress, the
CDN fetch measures worker→CDN ingress. Different links, different directions. But a reading of **0**
means "nothing measurable moved", which is a probe that did not work — and `--worker-min-mbit` would
have released four cards that then did the work while keeping the one that could not.

⇒ A measured reason the floor still defaults to `0.0`, and the reason #621 now writes the **whole**
probe map to `<rundir>/probe.json` — every candidate, every worker, with "threw" and "untested"
recorded distinctly from "measured 0". ⛔ Tip hour 4's run log was never saved into its run directory
at all, so that run's probe data is gone; this one survived only because `run.log` was kept.

## ⛔ #567 — NOT answered: the probe reports nothing

Every aggregate candidate came back **`cpu UNMEASURED`**, eight times, and the run said so plainly:

    ⚠ the executor's CPU was not measured, so execution cannot be attributed to it

The probe shipped in #597 does not produce a reading in practice. That is a finding in its own right
and cheap to chase — it needs no fleet.

⚠ **Chased the same day.** The probe was written in bash and `ssh.run` wraps its body in `sh -c`,
which is **dash** — so it had never once worked. Rewritten in POSIX `sh` and merged. ⛔ Unverified on
a fleet: the next run is the first time this will have produced a number.

📏 For the record: execution was **89.8 s over 3,088 segments**, with the first remote segment at
+10.1 s and 6 workers proving.

## ⛔ #607 — stage-ahead fired ZERO times, for the second time

Not once. The chain produced only two blocks in the hour and the fleet was never behind, so no
backlog ever formed — the only condition under which stage-ahead can fire.

Combined with the replay against tip hour 4's own timings (**0 of 4**), that is two independent runs
and a historical replay, all agreeing. **Stage-ahead is not the fix for #598**, as #608 already
conceded when compression replaced it. It is kept because it is free and correct when a backlog does
exist; it should not be described as the answer.

## ⭐ And /api/witness already serves these exact bundles, 18× faster

Measured 2026-10-01 against this run's own two blocks:

| height | bytes | this run's two-leg ssh path | `GET api.hazync.org/api/witness/<h>` |
|---|---|---|---|
| 969,305 | 29,756,765 | **73.5 s** | **3.41 s** |
| 969,306 | 26,893,180 | **25.1 s** | **1.38 s** |

```
0c54f7ef058eb48785883fb8e3d5c84f0d1d5d4f4351df403094ff17cf31e85a   from the API
0c54f7ef058eb48785883fb8e3d5c84f0d1d5d4f4351df403094ff17cf31e85a   the bundle this run proved
```

Byte-identical. `server.py`'s `bundle_path()` prefers `BRIDGE_DIR/bundle_<n>.json`, which **is** the
tip bundle, so the endpoint has always served it.

⇒ The orchestrator does not need to be in the path at all: the aggregate could fetch its own bundle,
and both legs collapse into one transfer that never touches a home uplink. Nothing new is exposed —
the endpoint is public and the bundle is public witness data. ⛔ But the coordinator is a different
box from the bridge and bundles crossed on a **60 s** timer, so the fix would have traded 25–73 s of
transfer for 0–60 s of waiting; #623 takes that to 15 s first. ⚠ And the pod→API leg is still
**unmeasured** — 1.38 s is to a laptop on a home connection, and one `curl -w` from an
already-rented card will settle it for free.

## What this run is good for

- ⭐ **Two aborted attempts cost $0.001 each.** Attempting a fleet is a nearly free probe; planning one
