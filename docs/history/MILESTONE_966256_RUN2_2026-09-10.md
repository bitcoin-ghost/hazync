# Reproducing it: block 966,256 proved again in 8.97 min on a different fleet

The [8.09-minute run](MILESTONE_966256_2026-09-10.md) was repeated on the **same block** with an
**entirely different set of rented machines**, two hours later. It came in at **538.0 seconds
(8.97 minutes)** and produced the **byte-identical receipt**.

```
### CONTINUOUS BLOCK PROOF: 538.0s = 8.97 min
### block 966,256 | 4,741 txs | 9,079 inputs | 27x RTX 4090
### cost $1.32
>>> PUSH-TRANSPORT RECEIPT VERIFIED against METHOD_ID
    digest 84e6643e531700811ee873ac5a4f5879a1424ecec813297948fee96f96ab84ff
```

| | run 1 | run 2 |

| wall clock | **485.2 s** | **538.0 s** |
| cards | 26 | 27 |
| chunk phase | 286.7 s | 322.1 s |

| aggregate | ~140 s | ~164 s |

| cost | $1.19 | $1.32 |
| digest | `84e6643e…` | `84e6643e…` |

**The digest is the result that matters.** Every chunk was proved on different silicon, and risc0
draws a fresh random challenge per segment (`rand_z`, see hazync#119), so no two runs share a single
intermediate. The receipt is nonetheless identical: it is a function of the block, not of the fleet,
the division of work, or the hardware. That is now **five independent reproductions** — two fleet
runs and three separate aggregates at 19, 21 and 26 workers.

## Run 2 was the harder run, and that is the point

Chunk 4 stalled **twice** — the hazync#147 signature, a live process with an idle GPU. Both times the
watchdog noticed the log had stopped growing, killed the prove, and handed the chunk to a card that
had already finished. Recovery cost about 35 s of the 53 s difference between the two runs.

Run 1 was clean. Run 2 hit real faults and still landed inside ten minutes. A number you can only get
when nothing goes wrong is not a capability.

## Fleet

27 × RTX 4090 — **US 11 · CA 6 · IS 5 · TW 3 · NO 1 · FR 1**, 10 driver versions, 12 CPU models.
Peaks: 22,478 MiB VRAM, 86 °C, 323 W. 5,649 samples at 1 Hz.

## ⚠ Two telemetry rows are not trustworthy

`summary.json` rows for chunks 0 and 4 carry `rc=101` with wall times that cannot be right (8.4 s for
85 segments). Both sit on cards involved in the stall/reassign path.

The **proof is unaffected** — 27 receipts were staged, the aggregate verified, and the digest matches
the first run exactly. But the *per-card timing* for those two chunks should be discarded, not
averaged in. Across the 25 clean rows the chunk-phase span is **275.5 s** over **1,851 segments**.

The likely cause is a result file written by a superseded attempt on the same card. `pod-prove.sh`
writes fixed filenames, and while reassigned work now runs in its own directory
(`/workspace/reN`), the *original* card keeps writing into `/workspace` until it is killed. Worth
fixing before these numbers are used for anything but the wall clock the driver measured directly.

## What broke on the way, and what it teaches

Three attempts failed before this one, **all of them in orchestration, none in the prover**:

1. **A stale receipt** made a 97-segment chunk report complete in 63 s. Those were *valid receipts
   for the same block*, so the proof would still have verified — only the timing would have lied.
   Pods are now cleared **and verified empty**, and the run aborts if any pod fails that check.
2. **A silently dropped `scp`** left the coordinator with 26 of 27 receipts; `seg-serve` panicked
   naming the missing file. Every copy is now retried and verified in both directions, and the staged
   count is asserted before the aggregate starts.
3. **A local path inside a remote command.** The stall check tested `[ -f $S/_reassigned ]` — a path
   on the operator's laptop, absent on the pod — so it always watched `/workspace/prove.log`, which
   on a reassigned card is its *first, finished* chunk's log. Static file ⇒ "stalled" ⇒ reassign ⇒
   repeat. Chunk 4 bounced across three healthy cards in a loop before this was spotted.

The pattern is worth naming: **every one of these produced a plausible wrong answer rather than an
error.** A fleet orchestrator's hard problem is not speed, it is refusing to report success it cannot
substantiate.

## Cost

**$1.32.** Two runs of a full Bitcoin block for **$2.51** of rented GPU time.

## Evidence

`hazync-milestone-966256-run2/` — 27 cards' `facts.json`, `result.json`, 1 Hz `gpu_samples.csv` and
`prove.log`; all **27 chunk receipts**; the aggregate log; `summary.csv`; the driver and pod scripts
as run; and `_reassigned` recording which chunks moved.

⛔ As with run 1, the **final aggregate receipt was not persisted** — `seg-serve` printed its digest
and exited. That is fixed in `4cad145` (the aggregate now honours `HAZYNC_OUT` and exits non-zero if
it verified but could not write), but this run used the published v0.21.0 binary, which predates the
fix. The receipt is regenerable from the 27 chunk receipts via `agg-chunks`.
