## The receipt exists

The first three runs of this block each verified and then lost the artifact — `seg-serve` (published
v0.21.0) verifies the aggregate in process, prints its digest and exits without an `fs::write`. The
fix was written as `4cad145` and landed on `main` squashed into `cadef1a` (#241); `4cad145` itself is
not on `main`. It was not in the v0.21.0 binary used for these runs (first release containing it:

### Two receipts, different bytes, identical journal

Run 3's receipt was regenerated the same way and is a **different file** —
sha256 `8eb3377ac7a986be73326ee8be7cc6372361580e9f01f5c05ad956a24698ea5b`, same 226,626 bytes — yet
carries the **identical** `journal_digest`. That is the expected result and it is worth stating
plainly, because comparing receipt SHAs has misled this project before: risc0 draws a fresh random
field element per segment in `preflight()`, so seal bytes are never reproducible. The **journal** is
a function of the block. Two independently produced receipts agreeing on it is the meaningful check;
their SHAs disagreeing is not a defect.

The digest `84e6643e5317…` has never differed across: the fleet aggregates of runs 1, 2 and 4 (25, 26
and 26 workers — a fleet of N cards has N−1 workers, the coordinator being the Nth); earlier fleet
aggregates recorded at the time at 19, 21 and 22 workers (no logs retained); the four #235 sweep
aggregates at N = 4, 8, 16 and 26 (`~/hazync-235-sweep/n*/agg.log`); and three solo `agg-chunks`
rebuilds (runs 2, 3 and 4). Run 3's own fleet digest was lost (see below).

- **Assembly is not the join tree.** It's the tail lift + the tree + a 27-step serial resolve chain

  narrow top levels) and the resolve chain are fixed.
- What survives: past ~16 cards, what's left of assembly is that floor, and more GPUs don't remove it.
  Run 4's 128.7 s against the ~17 s its 4090s' compute predicts is most likely geography: its cards
  spanned 6 countries, and every join and resolve is a coordinator round trip. That is **inferred, not
  measured**. → #235 (the sweep), #252 (the latency levers).

## What made this run clean

Runs 1–3 were all degraded by the orchestrator, not by the hardware, and every one of its bugs
produced a plausible wrong answer rather than an error. They are worth recording because they are
all the same mistake in different clothes — **inferring a fact instead of observing it.**

| bug | what it did |
|---|---|
| stall probe written in double quotes | `$(grep …)`/`$(stat …)` expanded on the *operator's laptop*, not the pod. The probe returned a constant, so every healthy card looked frozen and was killed at exactly the grace limit |
| stall inferred from log growth | the execute phase is CPU-only and silent for minutes; the first segment adds CUDA context creation and kernel JIT. Healthy cards were shot mid-work in three separate runs |
| `pgrep -cf seg-serve` | the remote shell's own command line contains the string, so it counts itself — a dead aggregate always reads as alive |
| `ps -eo comm \| grep "^hazync-host-cuda$"` | `comm` truncates at 15 characters, so this matches **nothing** — a live aggregate reads as dead. Acting on it relaunched `seg-serve` on top of a working one, which died on `bind()` while the original kept going with its log already unlinked |
| `rm -f agg.log` on a running aggregate | the live process kept writing to the deleted inode; when it exited, run 3's verified digest went with it |
| reassign on "receipt exists" | `chunk_N.bin` appears before the process releases ~22 GB of VRAM, so the new prove landed on a card still holding it → hazync#97 |

The stall detector no longer infers anything. It kills only on a **direct death signal** — no prove
process, or GPU utilisation under 5% *with* VRAM released — which cannot fire on a card that is
working. In run 4 it fired zero times.

The remaining fault was hardware: one Taiwan card died mid-prove (`gpu=0%`, `vram=1 MiB`, process
gone) in two consecutive attempts. It was swapped for a spare and run 4 ran without incident.

## Reproducing it

```sh
curl -fLO https://bitcoinghost.org/hazync/repro/block_966256.json.gz && gunzip block_966256.json.gz
sha256sum block_966256.json   # 41271d4f6ffd7048dc01caef62c5f1d223e34dd8737f8975d9c8927220d953a2

curl -fLO https://github.com/bitcoin-ghost/hazync/releases/download/v0.21.0/hazync-host-x86_64-linux-gnu-cuda
chmod +x hazync-host-x86_64-linux-gnu-cuda
./hazync-host-x86_64-linux-gnu-cuda method-id   # expect 37987b85…

# verify the published receipt without proving anything:
./hazync-host-x86_64-linux-gnu-cuda receipt-digest block_966256_run4.receipt
#   VERIFIED against METHOD_ID
#   journal_digest 84e6643e531700811ee873ac5a4f5879a1424ecec813297948fee96f96ab84ff

# or rebuild it from the 27 chunk receipts (~26 min on one 4090):
HAZYNC_LIFTX_HINT=1 HAZYNC_FIELD_BIGINT2=1 HAZYNC_ECMULT_WINDOW=21 \
HAZYNC_BLOCK=block_966256.json HAZYNC_CHUNKS=27 \
  ./hazync-host-x86_64-linux-gnu-cuda agg-chunks

# or prove it from scratch, one chunk per card, then aggregate (run 1's recipe, N=26):
export HAZYNC_LIFTX_HINT=1 HAZYNC_FIELD_BIGINT2=1 HAZYNC_ECMULT_WINDOW=21
export HAZYNC_BLOCK=$PWD/block_966256.json HAZYNC_CHUNKS=26
./hazync-host-x86_64-linux-gnu-cuda prove-chunk <0..25>     # one per card
# then, with all 26 chunk_N.bin in one directory:
HAZYNC_AGG=1 HAZYNC_PORT=9110 ./hazync-host-x86_64-linux-gnu-cuda seg-serve
```

⛔ `HAZYNC_LIFTX_HINT` and `HAZYNC_FIELD_BIGINT2` must match between build and run.

⛔ **On a consumer card you must first remove the CUDA forward-compatibility libraries**
(`mv /usr/local/cuda*/compat /usr/local/cuda*/compat.disabled; ldconfig`). They only work on
datacenter GPUs; on a 4090 CUDA fails with `Error 804: forward compatibility was attempted on non
supported HW` and sppark aborts with *"no CUDA-capable device is detected"* — while `nvidia-smi`
still cheerfully reports the card, so it reads as a code bug rather than an image bug.

## ⚠ CORRECTION: the two "recovered stalls" were self-inflicted

This document originally presented chunk 4's two stalls as the watchdog earning its keep. **That was
wrong, and the correction matters more than the claim did.**

Later debugging showed the stall detector switched to its tight 100 s limit as soon as `prove.log`
passed 200 bytes — but the liftx lines cross that during *setup*, while the execute phase is CPU-only
and legitimately emits nothing for a minute or more on a 9,079-input block. So the watchdog was
shooting healthy cards mid-execute. Chunk 4 "stalled" in **every** run for this reason.

Worse, the reassignment then landed on a card that had written its receipt but whose process still
held ~22 GB of VRAM, starting a second prove on one card — hazync#97 — which is the actual source of
the `rc=101` rows below.

So run 2 did not demonstrate fault recovery. It demonstrated an orchestrator generating faults and
then reporting its own cleanup as resilience. Fixed since: the grace period keys on whether proving
has actually begun, reassignment requires a genuinely idle card (no process **and** VRAM released),
and a card handed work is marked busy immediately.

✎ *Note on the correction above (kept verbatim), 2026-09-14:* run 2's `run/continuous.log` records
**three** stall-kills, not two — chunk 0 once (02:13:44) and chunk 4 twice (02:13:53, 02:14:51).
"Chunk 4 'stalled' in **every** run" is not true: run 1 used the same watchdog
(`SETUP_GRACE=240; STALL=100`) and its `continuous.log` has no stall lines, and run 4 had none. The
mechanism described is right; its reach is overstated.

## ⚠ Two telemetry rows are not trustworthy

`summary.json` rows for chunks 0 and 4 carry `rc=101` with wall times that cannot be right (8.4 s for
85 segments). Both sit on cards involved in the stall/reassign path.

The **proof is unaffected** — 27 receipts were staged, the aggregate verified, and the digest matches
the first run exactly. But the *per-card timing* for those two chunks should be discarded, not
averaged in. Across the 25 clean rows the chunk-phase span is **275.5 s** over **1,851 segments**.

**The cause is now known**: both cards ran two proves at once. `DONEC` was set when `chunk_N.bin`
appeared, but the writing process still owned the GPU, so the reassignment stacked a second prove on
top of a live one and both hit the hazync#97 memory failure. Chunk 0's own log shows it — `segment
83/83 136s elapsed`, a completed prove, followed by the OOM text from the second one. The receipts
were already written, which is why the run still verified.

## What broke on the way, and what it teaches

Three attempts failed before this one, **all of them in orchestration, none in the prover**:

1. **A stale receipt** made a 97-segment chunk report complete in 63 s. Those were *valid receipts
   for the same block*, so the proof would still have verified — only the timing would have lied.
   Pods are now cleared **and verified empty**, and the run aborts if any pod fails that check.
2. **A silently dropped `scp`** left the coordinator with 26 of 27 receipts; `seg-serve` panicked
   naming the missing file. Every copy is now retried and verified in both directions, and the staged
   count is asserted before the aggregate starts.
3. **A local path inside a remote command.** The stall check tested `[ -f $S/_reassigned ]` — a path
   on the operator's laptop, absent on the pod — so it always watched `/workspace/prove.log`, which
   on a reassigned card is its *first, finished* chunk's log. Static file ⇒ "stalled" ⇒ reassign ⇒
   repeat. Chunk 4 bounced across three healthy cards in a loop before this was spotted.

The pattern is worth naming: **every one of these produced a plausible wrong answer rather than an
error.** A fleet orchestrator's hard problem is not speed, it is refusing to report success it cannot
substantiate.

## What went wrong on the way

Three earlier attempts failed, and the failures are more useful than the success.

**A silent wedge.** One card printed its first log line and then sat at **0% GPU with a live process
for 14 minutes**. Nothing was watching, so it cost the entire attempt. ✎ This is the failure class of
hazync#147 (a 76-minute `prove-chunk` hang on block 962,000, filed earlier). The fix is a watchdog on
`prove.log` growth — *not* on GPU utilisation, because the execute phase is CPU-only and legitimately
shows 0% for 30–60 s on a block this size. (Run 2's correction above shows this log-growth watchdog
was itself wrong; run 4's detector acts only on a direct death signal.)

**hazync#119 — an invalid proof.** On another attempt chunk 15 aborted at segment 69 of 74 with
`verification indicates proof is invalid`, and wrote no receipt. It re-proved cleanly on a different
card. This run used the published v0.21.0 binary, which predates the segment-level retry in #240 and
the #119 fix in v0.21.1.

**Stale receipts nearly faked the result.** A pod still holding receipts from a previous attempt made
the orchestrator report a 97-segment chunk "complete" in 63 seconds. Because those were *valid
receipts for the same block*, the proof would still have verified — only the timing would have been a
lie. Pods are now cleared **and verified empty**, and the run aborts if any pod fails that check.

**Rented hardware is unreliable at a rate worth planning for.** Of 24 pods rented in the first batch,
8 had non-functional CUDA (`torch.cuda.is_available()` false, and restoring the compat libraries did
not help) and 8 never exposed SSH at all — a **33% yield**. Later batches ran better, but three
Canadian pods went network-dark mid-session while the provider still reported them RUNNING. The
answer is a cheap CUDA probe before the 410 MB binary is pushed, and terminating anything that fails.

⚠ **A crashed prove looks like the fastest card.** Failed runs return in 10–25 s and sort to the top
of a speed ranking. Screening must gate on `rc=0` before it ranks on time, or it selects the broken
machines.

(The wedge duration, the chunk-15 fault and the pod-yield counts come from attempts whose logs were not
retained; they are recorded as written at the time.)
