=== 4. THE GPU IDLE GAP IS A SINGLE-THREADED HOST SECTION (derived 2026-08-21 from the archived vmstat) ===

  Section 3 left this open: "the ec-bench workload cannot see this — its vmstat shows the host 84.4%
  idle ... measuring a real chunk prove with vmstat is what separates the two, and is run 2."

  Run 2's vmstat was captured before the box was deleted. Both logs, averaged identically over every
  18-field data row (us=$13, sy=$14, id=$15, wa=$16):

    vmstat-run2.log  (real chunk prove, 483 samples ~2 s => ~966 s, matches the 978 s run)
        run queue 1.02   us 7.2%   sy 1.1%   id 91.9%   wa 0.0%    host >=90% idle in 99.6% of samples
    vmstat-139.log   (ec-bench microbench, 137 samples)
        run queue 1.04   us 7.4%   sy 0.9%   id 91.8%   wa 0.0%    host >=90% idle in 99.3% of samples

  >>> THEY ARE THE SAME. The real chunk prove does NOT saturate the host either, so the hypothesis
      that section 3 offered for the 25.1% GPU idle — that a real prove does heavy host-side witness
      generation the microbench does not — IS REFUTED BY THE RUN THAT WAS SUPPOSED TO CONFIRM IT.

  WHAT IT IS INSTEAD. us 7.2% of 12 cores = 0.86 cores busy, at a run queue of 1.0, with wa = 0.0%.
  That is ONE thread, and no I/O wait. The quarter of the run where the GPU is idle is a SERIAL
  host-side section, not a parallel host workload starved of cores.

  CONSEQUENCES:
    - More host cores cannot close the gap. Neither can a faster card (result 1) nor concurrency
      (result 2). All three now have the same explanation, which no single one of them established.
    - It is not I/O. wa is 0.0% across all 483 samples, so it is not the archive node, not the disk
      and not the offsite copy.
    - It IS plausibly the "host-side tree-fold (log-depth aggregation, the rest of the ~14% fold
      overhead)" already listed in docs/ACCELERATION.md as a remaining maximal-Core lever. That lever
      was parked as a modest tidy-up; on this evidence it is the ONLY measured lever left, and it is
      worth ~25% of chunk wall-clock before any accelerator work multiplies its share.

  ⚠ NOT ESTABLISHED: WHICH serial section. vmstat proves one thread and no I/O; it does not name the
  code. A profile of the host process across a chunk prove is the next measurement, and unlike
  everything else in this file it needs no GPU rental — the serial section is host-side by definition.

  ⚠ The 84.4% quoted in section 3 does not reproduce as 91.8% here; the averaging method behind it is
  unrecorded. The load-bearing comparison is run2 vs 139 computed identically, and that is above.
